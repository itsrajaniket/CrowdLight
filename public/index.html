Protocol

In-Browser NTP Time Alignment

Mobile networks suffer from variable packet latency. Instead of executing commands on arrival, CrowdLight runs a 5-ping NTP exchange on socket connect, computing client-server clock offset while filtering latency spikes:

serverTime = performance.now() + clockOffset

All lighting triggers dispatch with an executeAt future timestamp, executing synchronously on requestAnimationFrame.

Payload Budget

19.3 KB Zero-Framework Bundle

In stadium environments with 40,000 phones connected to congested cell towers, 50 MB apps fail to download. CrowdLight was built strictly with pure vanilla ES6+ and CSS3:

HTML: 1.1 KB | CSS: 4.8 KB | JS: 13.4 KB

Transfers in under 50ms over 3G/4G, bypassing app store gatekeepers and permissions entirely.

Scalability

Pre-Serialized WebSocket Hub

Serializing JSON payloads inside a 500-client broadcast loop causes severe garbage collection pauses. CrowdLight pre-serializes string buffers once prior to fan-out:

const msg = JSON.stringify(payload);
clients.forEach(c => c.send(msg));

Sustains 500+ concurrent connections on a single low-spec Node.js process using less than 60 MB of system RAM.

TECHNICAL SPEC & FAQ

Frequently Asked Questions

Honest architectural answers to the most common operational and tour-director questions.

📱 Do attendees need to download an app or sign up?

No. Zero app store downloads, zero registrations, zero permissions beyond screen brightness. Attendees simply open their native phone camera, point it at the stage screen QR code, and the web app loads in under 300ms in Safari, Chrome, or any mobile browser.

📶 Do phones need an active internet connection?

Yes. Attendees connect via standard venue Wi-Fi or cellular data (4G/LTE/5G). Because the initial bundle is under 20 KB and ongoing WebSocket pings consume less than 1 KB per minute, CrowdLight stays connected even under congested stadium cell towers where heavy apps time out.

👥 How many people can it handle simultaneously?

Honest benchmark: A single free Node.js core instance (like this live Render cloud demo) has been stress-tested to 500+ simultaneous phones with zero dropped frames. In production for 20,000–80,000 seat stadiums, CrowdLight scales horizontally via Docker containers backed by a lightweight Redis Pub/Sub adapter.

🔋 Does keeping screens on drain phone batteries?

Minimally. CrowdLight keeps the screen illuminated only during active musical cues via the Screen Wake Lock API. During pauses and blackouts, all GPU animation loops are instantly paused and the screen turns to pure OLED black (#000000), consuming up to 80% less power than typical concert video recording.

⏱️ What if an attendee's phone clock is wrong or network has lag?

CrowdLight never relies on the user's phone clock. When an attendee joins, the app runs a 5-ping NTP clock synchronization burst that computes the exact server-client time offset and rejects latency spikes. All lighting commands are sent with a future executeAt timestamp, ensuring millisecond-level lockstep synchronization across iOS and Android alike.

🔒 Can audience members hijack or control the lights?

No. The WebSocket server strictly enforces role-based authorization. Audience connections are assigned a read-only role. Only sessions that authenticate with the cryptographically verified controller PIN can broadcast lighting cues to the crowd.
